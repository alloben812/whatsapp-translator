# Подключение к MultiModeAgents

План для приватного репозитория `alloben812/whatsapp-translator`. Проверено по исходникам и документации `alloben812/multimode-agents` 18 сентября 2026 года; опорный commit — `8cd97d5a2c0f8dd2fb32eae087adc69fac497c5c`. Состояние установки на Hetzner в этой проверке **не проверялось**. Импорт, серверные задания и вызовы моделей не выполнялись.

## Для чего используем существующий проект

MultiModeAgents можно использовать для обсуждения кода, ограниченных задач разработки и независимого ревью WhatsApp Translator. Сам перевод сообщений остаётся отдельной функцией WhatsApp Translator.

По README MultiModeAgents, доступы к Codex и Claude настроены через подписочные CLI и изолированных Linux-пользователей. Это не API-ключ для перевода и не готовый HTTP endpoint для ответа на каждое сообщение WhatsApp. Подключение репозитория не переносит подписочные сессии, не предоставляет доступ к WhatsApp и не добавляет GitHub-права процессам моделей.

| Возможность | Задокументированный механизм | Что он не делает сам |
| --- | --- | --- |
| Обсуждение проекта в общем чате | Импорт выбранных файлов на точном commit, режим `read_snapshot` | Не читает произвольные файлы, не выполняет команды, не создаёт PR |
| Подготовка разработки и ревью | `project-job.js prepare / capture / accept` | Не запускает модели и тесты, не делает merge |
| Один цикл разработки на VPS | `mma-server-project`: Codex → изолированные Node-тесты → Claude review | Не включает расписание, автоматический допуск по квоте или merge |
| Перевод WhatsApp в работающем сервисе | Отдельный адаптер перевода в WhatsApp Translator | Нельзя считать его доступным только из-за наличия входа в Codex/Claude |

## 1. Подготовить кодовый проект

1. Создать приватный GitHub-репозиторий и отправить начальный проверенный commit.
2. На компьютере оператора или сервере получить обычную локальную Git-копию нового репозитория. Для приватного репозитория нужны отдельные права GitHub у доверенного оператора; они не должны попадать в задания моделей.
3. Зафиксировать полный SHA исходного commit. Импорт работает с сохранёнными Git-объектами; незакоммиченные изменения в него не входят.
4. Убедиться, что в выбранных файлах нет секретов, WhatsApp-сессии, QR, телефонов или содержимого переписки. Для обсуждения архитектуры достаточно документации и кода.

Отдельный репозиторий не требует копировать настройки авторизации из MultiModeAgents. Развёртывание приложения, WhatsApp-сессия и настройка провайдера перевода выполняются отдельно от подключения проекта к разработке и ревью.

## 2. Подключить проект к общему чату

Этот шаг регистрирует снимок для обсуждения. Он ещё не даёт агентам возможность изменять проект.

Перед исполнением на целевом хосте нужно установить фактические пути к установленному MultiModeAgents, Git-копии WhatsApp Translator и базе чата, а также владельца базы. Нельзя угадывать путь базы или запускать CLI от произвольного пользователя.

Синтаксис экспорта из корня MultiModeAgents:

```sh
python3 scripts/import-chat-project.py \
  --repo /absolute/path/to/whatsapp-translator \
  --commit FULL_40_CHARACTER_COMMIT \
  --expected-url https://github.com/alloben812/whatsapp-translator \
  --project-id whatsapp-translator \
  --title 'WhatsApp Translator' \
  --path README.md \
  --path package.json
```

JSON-вывод передаётся через stdin следующей команде, выполняемой владельцем **существующей** базы чата:

```sh
node dist/src/chat-project-cli.js /absolute/canonical/path/chat.sqlite import
```

Вызов выше показывает синтаксис; отдельно без JSON на stdin он не импортирует проект. Экспорт и импорт можно соединить каналом только после проверки пользователя и путей. CLI требует абсолютный канонический путь, закрытые права и совпадение владельца процесса с владельцем базы и каталога. Документация предписывает каталог `0700`, файл `0600`, без симлинков и дополнительных hardlink.

После импорта проект можно выбрать в веб-интерфейсе. Административная альтернатива для существующей комнаты `main` — передать JSON `{"roomId":"main","projectId":"whatsapp-translator"}` на stdin того же CLI с операцией `bind`. Операция `list` принимает `{}` и показывает зарегистрированные проекты без содержимого файлов.

Проверка результата: в пульте должны появиться нужные GitHub URL, полный commit и список импортированных файлов. Новый вопрос получает этот снимок; уже заданные вопросы сохраняют прежний. После изменения кода для нового обсуждения потребуется повторный импорт.

Ограничения: 1–8 текстовых файлов, исходный файл до 1 MiB, общий контекст до 12 000 байт вместе с метаданными и JSON escaping. Большие тексты сокращаются с признаком `excerpt: true`; такой снимок нельзя выдавать за полное ревью кода. Путь `origin` должен совпадать с ожидаемым GitHub URL. Известные форматы секретов фильтруются, но фильтр не гарантирует отсутствие любого секрета.

## 3. Передавать небольшие изменения на разработку и ревью

Для локального проектного цикла задача описывается отдельным JSON с полями `goal` и `acceptanceCriteria`. Из корня собранного MultiModeAgents:

```sh
node dist/src/project-job.js prepare \
  /absolute/path/to/whatsapp-translator \
  FULL_40_CHARACTER_COMMIT \
  /absolute/path/to/task.json \
  /absolute/path/to/new-job
```

Команда создаёт независимую Git-копию в `new-job/work/`; исходный репозиторий не меняется. Каталог задачи должен быть новым, а его родитель — существующим. В рабочую копию не переносятся remotes и настройки авторизации. Копия сама по себе не является изоляцией операционной системы.

Дальнейший порядок:

1. Исполнитель меняет код в `work/`, выполняет подходящие проверки и создаёт commit. Для параллельной работы нужны отдельные копии и ветки от общего исходного commit.
2. Оператор сохраняет результаты фактически выполненных проверок в `validation.json` вне `work/`; не подставляет `passed` для непроверенного запуска.
3. `project-job.js capture JOB VALIDATION_JSON` собирает пакет по точным base/head; рабочая копия должна быть чистой.
4. Независимый проверяющий получает сформированный `prompt.txt` и возвращает `pass` либо `changes_requested` в требуемом JSON.
5. `project-job.js accept JOB ATTEMPT_DIRECTORY_NAME REVIEW_JSON` проверяет привязку результата к задаче, commit, хешам и nonce.
6. После объединения параллельных изменений тесты и окончательное ревью выполняются на объединённом commit. Последующие правки требуют нового пакета и ревью.

Локальный пакет ограничен 16 изменёнными текстовыми файлами и 60 KB prompt с обоими снимками и JSON escaping. Работа делится на небольшие изменения. `readyForOperator: true` — предложение к приёмке конкретного commit, не автоматическое разрешение merge. Автоматическая публикация PR в этом механизме не заявлена.

## 4. Перенести один цикл на Hetzner

Сначала после получения SSH-доступа нужно сверить фактическую установленную версию, наличие `mma-server-project`, состояние изоляции и действующий механизм дневного допуска. Документация GitHub не доказывает, что всё это сейчас установлено и готово на сервере.

Задокументированный цикл:

1. Подготовить пакет с точным `baseCommit`, целью, критериями, разрешёнными путями, моделями, сроком и Git bundle.
2. Доверенный оператор передаёт JSON на stdin `mma-server-project stage PACKAGE_ID`.
3. Stage фиксирует пакет и его hash. Отдельная административная сторона выдаёт связанный с этим пакетом `permit.json`; start сам разрешение не создаёт.
4. Должен быть установлен root-owned `/usr/local/sbin/mma-server-project-admit`. Перед каждым модельным этапом он проверяет дневной допуск. Одноразовое разрешение пакета не отменяет дневной лимит.
5. `mma-server-project start PACKAGE_ID` запускает coordinator в systemd. `status`, `result` и `bundle` читают состояние и результат; `stop` выполняет остановку с проверкой дочерних исполнителей.

В отличие от локального task JSON, серверный manifest использует поле `criteria`, а не `acceptanceCriteria`, и явно задаёт `allowedPaths`. Нельзя отправить локальный файл задачи как серверный пакет без преобразования и Git bundle.

Ограничения серверного пакета: 1–8 редактируемых файлов, Git bundle до 16 MiB, весь JSON до 24 MiB, срок не более 30 минут от staging. После неопределённого запуска нельзя повторять inference автоматически. После перезагрузки или частичного выполнения автоматическое возобновление не предусмотрено. Закрытие SSH или Mac не останавливает уже запущенный systemd coordinator.

Документирован smoke-тест Linux без моделей: `verify-server-project.py --execute`. Он создаёт тестовые пакеты и units, поэтому это отдельная серверная проверка с побочными эффектами, а не read-only диагностика. Здесь он не запускался.

## Что проверить при следующем подключении

- GitHub: репозиторий и ожидаемый commit доступны доверенному оператору.
- MultiModeAgents: установленная ревизия и реальная поддержка описанных команд совпадают с планом.
- Общий чат: найден владелец и путь базы; снимок импортирован и отображается с правильным commit.
- Серверный цикл: изоляция, admission hook и действующие квоты проверены до запуска модельного задания.
- WhatsApp Translator: отдельно выбран и проверен переводчик; его секреты и WhatsApp-сессия не передаются в пакеты MultiModeAgents.
